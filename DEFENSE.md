# Защита проекта по аренде жилья

План рассчитан на 7–10 минут вместе с вопросами. Перед показом запустите
Compose, откройте каталог и подготовьте две независимые сессии клиента API.
Для запросов с телом используйте JSON. В README перечислены маршруты и порядок
получения CSRF-токена.

| Время | Что показать и объяснить |
| --- | --- |
| 0:00–0:45 | Цель сервиса — дать арендодателю возможность опубликовать жильё, а арендатору найти его и забронировать. Покажите список двух контейнеров и объясните, что том MySQL переживает перезапуск приложения. |
| 0:45–1:45 | Откройте модели User, Listing, Booking, Review. Пройдите по связям от объявления до отзыва. Один человек может состоять в группах renter и landlord. Право на изменение конкретного объявления определяется его владельцем. |
| 1:45–3:00 | В первой сессии подключите landlord и создайте объявление. Во второй найдите его по городу, цене и слову из описания. Откройте карточку, затем покажите популярный запрос. |
| 3:00–4:30 | Во второй сессии создайте бронь. Повторите запрос на пересекающиеся даты. Покажите ошибку и объясните, что обе транзакции берут блокировку одной строки объявления перед поиском пересечений. |
| 4:30–5:30 | Покажите подтверждение владельцем и запрет подтверждения арендатором. Объясните интервал дат: выезд и новый заезд в один день совместимы. Отмена разрешена вплоть до даты заезда минус два дня включительно. |
| 5:30–6:30 | Откройте tests/test_rental.py. В тесте управляются календарные даты: до выезда отзыв отклоняется, после завершённого проживания он принимается, повторная отправка отклоняется. |
| 6:30–7:00 | Покажите GitHub Actions: сборка Compose, тест с двумя соединениями MySQL и проверка сохранности записи после перезапуска. |
| 7:00–10:00 | Вопросы и демонстрация интересующего преподавателя участка кода. |

## Пример для показа

Тело запроса POST /api/listings/ от имени арендодателя:

```json
{"title":"Studio am Park","description":"Quiet studio near the station","city":"Berlin","district":"Mitte","nightly_price":"80.00","rooms":1,"housing_type":"studio"}
```

Затем выполните GET /api/listings/?city=Berlin&max_price=100&search=station.
Скопируйте ID объявления. В POST /api/bookings/ передайте его в поле listing,
а в start_date и end_date — будущие даты в формате YYYY-MM-DD.
Скопируйте ID брони и отправьте PATCH /api/bookings/{id}/status/
с телом `{"status":"confirmed"}` в сессии владельца.

## Три вопроса по реализации

**Почему для отзыва достаточно booking_id?** Через бронь известны и арендатор,
и объявление. Уникальное ограничение на booking_id допускает один отзыв за
проживание. Тот же человек может оставить второй отзыв после другой поездки.

**Что предотвращает двойное бронирование, если таблица броней пока пуста?**
Объявление уже существует. Сервис блокирует эту строку в транзакции даже
при отсутствии броней. После получения блокировки он проверяет пересечение
start_date < новый выезд и end_date > новый заезд для действующих броней.

**Почему раздельно проверяются группа и владелец?** Группа позволяет создать
объявление. Запрос изменения или удаления ищет объявление среди объектов
текущего владельца. Участник второй группы может при этом снимать чужое жильё.
